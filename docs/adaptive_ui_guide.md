# Пособие: адаптивный UI в Godot 4

Разбор реального бага главного меню (`scenes/ui/main_menu.tscn`) — почему текст
уезжал за левый край окна на нестандартных разрешениях, как это было
диагностировано и как избежать этого в новых экранах.

## Симптом

Левая панель меню (заголовок, подзаголовок, кнопки) была построена на
процентных якорях (`anchor_right = 0.38` — 38% ширины окна). На большом окне
всё выглядело нормально. На узком окне (~1160px) текст обрезался слева:
первые буквы заголовка и кнопок уезжали за пределы окна, будто панель сдвинута
влево на десятки пикселей — хотя разделительная линия панели стояла на
правильных 38%.

## Как диагностировали

Screenshot тут не помог — по картинке видно *что* сломано, но не *почему*.
Вместо гадания добавили временный debug-print прямо в `_ready()` сцены и
подписались на `size_changed` вьюпорта, чтобы значения печатались при каждом
ресайзе окна:

```gdscript
func _ready() -> void:
    get_tree().root.size_changed.connect(_debug_print_rects)
    _debug_print_rects()

func _debug_print_rects() -> void:
    var cm: Control = $LeftPanel/ContentMargin
    print("viewport=", get_viewport_rect().size)
    print("LeftPanel=", $LeftPanel.get_global_rect())
    print("ContentMargin anchors=", cm.anchor_left, cm.anchor_top, cm.anchor_right, cm.anchor_bottom)
    print("ContentMargin offsets=", cm.offset_left, cm.offset_top, cm.offset_right, cm.offset_bottom)
    print("ContentMargin min_size=", cm.get_combined_minimum_size())
    print("ContentMargin=", cm.get_global_rect())
```

Запустили сцену через `godot ... scenes/ui/main_menu.tscn`, окно ресайзили
через `MoveWindow` (WinAPI) снаружи — и в логе увидели:

```
LeftPanel      = [P: (0, 0),        S: (437.76, 648)]
ContentMargin anchors = 0, 0, 1, 1      ← честный FULL_RECT
ContentMargin offsets = 0, 0, 0, 0      ← без сдвигов
ContentMargin min_size = (759, 462)     ← а вот и проблема
ContentMargin  = [P: (-160.62, 0),  S: (759, 648)]
```

Якоря и офсеты правильные (`FULL_RECT`, `0,0,0,0`), но фактический прямоугольник
— `position.x = -160.62`, `width = 759`, хотя родитель (`LeftPanel`) шириной
всего `437.76`. Разница `(759 − 437.76) / 2 ≈ 160.6` — **ровно** тот самый
отрицательный сдвиг.

## Причина

Это не баг Godot, а задокументированное (но неочевидное) поведение якорной
системы: если `min_size` контрола **больше**, чем прямоугольник, который дают
якоря, Godot не может сделать контрол меньше минимума — но и не растягивает
его вправо/вниз. Он **расширяет прямоугольник симметрично от центра**
исходной якорной области. Половина лишней ширины уходит вправо, половина —
влево, в минус. Это применяется к контролу целиком, независимо от
`size_flags_horizontal` — эти флаги работают только когда родитель сам
является `Container`; здесь родитель — `Panel` (просто `Control` с фоном), а
не `Container`, так что `size_flags` тут не при чём.

`min_size = 759` взялся не из констант вроде `custom_minimum_size`, а из
`Label`-ов **без** `autowrap`: `SubtitleLabel` содержал длинное предложение
одной строкой, и Godot для не оборачиваемого текста ставит `min_size.x` равным
ширине **всего** текста целиком. 38% узкого окна физически не могли вместить
несокращаемую ширину такого лейбла — отсюда and expansion from center.

## Правило на будущее

> **Любой `Label` с текстом переменной/непредсказуемой длины внутри
> процентно-анкоренного (не пиксельно-фиксированного) контейнера обязан иметь
> `autowrap_mode` включённым.**

Без autowrap у Label нет верхней границы `min_size.x` — он всегда требует
ширину всей строки. С `autowrap_mode = TextServer.AUTOWRAP_WORD` (значение
`2`) минимальная ширина падает до ширины **одного самого длинного слова**, а
не всей фразы:

- если реального места достаточно — строка всё равно рисуется в одну линию
  (перенос сработает, только когда ширины действительно не хватает);
- если места мало — текст красиво переносится на 2–3 строки вместо того,
  чтобы утащить весь контейнер в минус и обрезать его за пределами окна.

Это же правило действует не только для лейблов: **любой `custom_minimum_size`
с константой в пикселях**, поставленный сиблингом внутри общего
`VBoxContainer`/`HBoxContainer`, тоже раздувает общий `min_size` контейнера и
может вызвать тот же эффект (так и было — `custom_minimum_size = Vector2(320, 0)`
на `ButtonsContainer` тоже убрали при рефакторинге).

## Чек-лист адаптивного экрана в Godot

1. **Не ставь фиксированные пиксельные `custom_minimum_size`** на элементы
   внутри контейнеров, которые сами сидят в процентных якорях. Если нужна
   нижняя граница ширины — сначала спроси себя, влезет ли она в самое узкое
   ожидаемое окно.
2. **Включай `autowrap_mode` на всех `Label`, где текст не жёстко короткий**
   (заголовки, подписи, подсказки, любой текст на другом языке — кириллица
   часто шире латиницы при том же смысле).
3. **`clip_contents = true` на корневой панели** — не решает проблему само по
   себе, но превращает "текст вылетает за окно" в "текст аккуратно обрезан
   границей панели", что не так фатально, если где-то всё-таки останется
   недосчитанный край.
4. **Не верь одному скриншоту на одном разрешении.** Явный баг проявляется
   только при определённых соотношениях ширины панели и содержимого — тестируй
   минимум два случая: узкое окно (~1150–1200px) и широкое (1920px+).
5. **Если правка "не помогает" визуально — не гадай, печатай числа.**
   `get_global_rect()`, `anchor_*`, `offset_*`, `get_combined_minimum_size()`
   прямо в `_ready()` + подписка на `size_changed` дают точный ответ за одну
   итерацию вместо десятка скриншотов вслепую.

## Как быстро проверить экран на резинового поведение

```powershell
# Ресайз окна запущенной игры без потери фокуса/без пересборки — правишь .tscn,
# перезапускаешь, дёргаешь MoveWindow на разные размеры и сравниваешь.
Add-Type @"
using System;
using System.Runtime.InteropServices;
public class Win { [DllImport("user32.dll")] public static extern bool MoveWindow(IntPtr hWnd, int X, int Y, int nWidth, int nHeight, bool bRepaint); }
"@
[Win]::MoveWindow($proc.MainWindowHandle, 0, 0, 1160, 700, $true)   # узко
[Win]::MoveWindow($proc.MainWindowHandle, 0, 0, 1920, 1040, $true)  # широко
```

Скриншотить не обязательно окно в фокусе — `PrintWindow` (WinAPI) снимает
содержимое конкретного `hWnd` независимо от того, какое окно активно, что
надёжнее, чем `CopyFromScreen` в автоматизированном тестировании.
